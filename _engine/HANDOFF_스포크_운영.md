## 2. ⭐ 제목 뽑는 순서 (여기가 승부처)

### 2-1. 공식

```
[한정어] + [핵심키워드] + [행동어]
```

- **핵심키워드** — 그날 허브의 focus keyword를 **글자 그대로** 쓴다. 바꾸지 않는다.
- **한정어** — 경쟁을 낮추는 장치. 아래 4종 중 하나를 반드시 붙인다.
  1. 지역 : `영동군` `통영시` `전북` (시·군 단위가 가장 강함)
  2. 대상 : `차상위계층` `1인가구` `탈퇴 회원` `가족 명의`
  3. 시점 : `8월` `추석 전` `마감 임박` `2차`
  4. 상황 : `전입` `앱 안 될 때` `문자 왔을 때` `안 보여요`
- **행동어** — `신청` `조회` `대상` `금액` `기준일` `언제` `방법`

### 2-2. 배분 — 소재 유형부터 판정한다

> **판정법**: 소재 앞에 시·군·구를 붙여서 말이 되면 A, 안 되면 B.
> ("영동군 민생지원금" → A / "따릉이 개인정보 유출" → B)

| | A형 (지역 분화 가능) | B형 (전국 이슈·사건) |
|---|---|---|
| 지역형 | 5 | — |
| 대상형 | 3 | 4 |
| 상황·문제형 | 2 | 4 |
| 절차·금액형 | — | 2 |

### 2-3. 제목 창고는 지식iN이다

지어내지 않는다. 네이버 지식iN에 실제로 올라온 질문을 **그대로 제목화**한다.
2026-08-09 세트의 3·4번이 그 방식으로 나왔다
("따릉이 이용해본 적도 없고 서울에도 안 사는데 해당자라고 문자가 왔어요").

보조 창고: 네이버 연관검색어, 자동완성, 카페 질문글.

### 2-4. 제목 금지사항

- 근거 없는 금액·날짜 단정 ("○○원 나온다")
- 확정 안 된 것을 확정으로 ("지급 확정")
- 같은 문장 구조 10개 반복 — 어미와 길이를 섞는다

### 2-5. 실측 참고 — 상위 노출 경쟁글 제목 패턴

> **출처 주의.** 원래 벤치마킹 대상이던 `m.blog.naver.com/andudtk12/*` 5건은
> **도메인 정책 차단으로 열지 못했다** (브라우저·WebFetch·인앱 3경로 전부 차단).
> 아래는 대체 근거다 — 네이버 검색API로 같은 소재(따릉이 유출·보상)의
> 유사도순·최신순 **120건 제목**을 수집해 뽑았다. 2026-08-10 수집.
> 본문을 못 읽었으므로 **이미지 배치 · 외부링크 위치와 문구 · 글 길이 ·
> 해시태그 총 개수는 여전히 미확인**이다. 그 4가지는 여기 적지 않았다.

1. **`｜` 로 검색어 2세트를 한 제목에 적재** — 2-1 공식에 없던 패턴이다.
   `[한정어+키워드+행동어]` 를 쓰고 `｜` 뒤에 **다른 행동어 세트**를 붙인다.
   - `따릉이 개인정보 유출 조회 방법｜30일 정기권 보상 대상·신청 여부`
   - `따릉이 개인정보 유출 보상｜30일권 지급일·유출 항목 총정리`

   롱테일 2개를 한 글로 먹는다. 제목이 길어지므로 **10건 중 2~3건만** 쓴다.
2. **자기대입 의문형 후크** — `나도 대상자일까?` `설마 내 정보도?` `내 정보도 포함됐을까?`
   2-3(지식iN 질문 원문을 제목화)과 잘 붙는다.
3. **숫자를 제목 앞쪽에** — `462만 명` `5,000원` `30일` `3개월`.
   단 2-4 금지사항대로 `_set_*.py` 에 없는 숫자는 쓰지 않는다.
4. **논란 프레임** — `고작` `딸랑` `허탈한` `털렸다`.
   **B형(전국 이슈)에서만** 쓴다. A형(지역 분화)에는 안 맞는다.

## 3. 본문 뽑는 법 — 슬롯 8칸을 채우면 끝

**재료는 새로 조사하지 않는다.** 그날 허브 세트 파일(`wp_lite/_set_YYYYMMDD.py`)에
이미 검증된 사실이 다 들어 있다. 거기서 옮긴다.

| 슬롯 | 내용 | 어디서 가져오나 |
|---|---|---|
| `intro` | 2문장, 결론 먼저 | 허브 `lead` |
| `table` | 3행 (대상/금액/기한) | 허브 `sum_rows` |
| `sub1` | 📌 궁금증형 소제목 | 새로 (질문형 X, "왜 안 보일까" O) |
| `body1` | 3~4문장, 답 | 허브 `faq` 답변 |
| `cta_mid` | 답 주기 직전 허브 링크 | 고정 |
| `warns` | 2~3줄 (기준일·기한·스미싱) | 허브 `WARN` |
| `cta_end` | 스포크 링크 (check 또는 apply) | 고정 |
| `question` | 여운형 질문 | 새로 |

해시태그 8개는 허브 `tags`를 확장한다. `#경제` `#일상` 같은 광범위 태그는 금지.

### 3-1. 링크 삽입 규칙 (어기면 유입이 안 생긴다)

글 1개당 링크는 **정확히 2회, 둘 다 메인허브**. 그리고 **형태가 서로 다르다** (2026-08-10 확정).

| | 위치 | 형태 | 노리는 것 |
|---|---|---|---|
| ① | 본문 **25~35%** | 카드 또는 텍스트 링크 | 크고 눈에 띈다 → 클릭 |
| ② | **최하단** (노트 뒤) | 👉 텍스트 링크 | 끝까지 읽은 사람에게 마지막 기회 |

**본문에는 두 곳 다 URL 주소를 그대로 박는다.** 붙여넣으면 두 곳 모두 텍스트 링크가 된다.

> ①을 **이미지 카드**로 만들고 싶으면 그 줄만 잘라내 다시 입력하고 엔터를 친다.
> 카드는 **URL이 단독으로 입력되고 엔터**여야만 생긴다(실측). 텍스트 링크로 둬도
> 동작에는 문제가 없으므로, 급할 때는 그냥 붙여넣고 끝내도 된다.
>
> 2026-08-10 이전에는 ①에 마커를 넣고 사람이 주소를 찾아 입력하게 했는데,
> 복붙할 때 번거롭다는 피드백이 있어 실제 주소를 박는 방식으로 바꿨다.

**⛔ 맨 위(썸네일 근처)에는 절대 링크를 넣지 않는다.**
읽기도 전에 나가서 체류시간이 무너진다. 네이버가 "외부 유출 목적 글"로 볼 여지도 커진다.
**중간과 최하단 두 곳만** 노린다.

### 3-1-a. ⭐ 눌릴 수밖에 없는 구조 — 무엇을 아끼는지가 전부다

정보를 100% 주면 허브를 누를 이유가 사라진다. 그렇다고 통째로 감추면
네이버가 낚시로 잡는다(4절 doorway page · 5절 "근거 없이 자극만 = 이탈").
**그래서 아끼는 대상을 정확히 골라야 한다.**

| | 다룰 것 | 왜 |
|---|---|---|
| **다 준다** | 사실 · 관점 · 논평 · 배경 | 아끼면 홈판에서 죽는다. 관점 경쟁이 홈판의 본질이다 |
| **아낀다** | **"내 케이스는 어떻게 되나"** | 경우의 수가 갈리는 지점. 허브 위젯이 실제로 더 잘 답한다 |

이건 정보를 숨기는 게 아니라 **역할 분담**이다. 블로그는 **규칙**을, 허브는 **판정**을 맡는다.
경우의 수가 많아 본문에 다 못 쓰는 내용이라 독자도 납득한다.

**따릉이 사례 (2026-08-10)**

```
블로그가 주는 것   유출 기간 2024.6.28~29 · 보상 내용 · 3개월 기한 · 스미싱 주의
                   → 사실은 전부 준다

허브로 넘기는 것   가입 시기가 유출 기간에 걸치나
                   탈퇴자·번호 변경자·가족 명의·비서울 거주자는 각각 어떻게 되나
                   기존 정기권 보유자의 소멸일은 언제인가
                   → 케이스가 갈려서 본문에 다 못 쓴다
```

**배치 공식**

```
도입 3문장         결론 먼저 (사실)
📌 챕터1           "기준이 이래서 경우가 갈린다"를 보여주고 갈래를 나열
                   답을 주지 않고 "본인이 어느 갈래인지는 맞춰봐야 나온다"로 닫는다
{{URL_CARD}}       25~30% 지점 ← 궁금증이 최고조일 때
📌 챕터2~3         원리·관점은 다 준다. 다만 "내 계정은 조회해봐야" 를 한 번 더 심는다
📌 챕터4           또 하나의 갈래 (예: 소멸일이 사람마다 다르다) → 아쉬움 유지
📝 노트            "여기까지는 모두 같지만 OO와 OO는 사람마다 갈립니다"
{{URL_TEXT}}       ① 을 안 누른 사람에게 마지막 기회
```

핵심은 **아쉬움을 한 번 주고 끝내지 않는 것**이다.
챕터마다 갈래를 하나씩 심어두면, 첫 링크를 지나친 사람도 마지막에 누른다.

> ⛔ **없는 갈래를 지어내지 않는다.** 실제로 케이스가 안 갈리는 소재라면
> 그냥 다 주고 링크는 "더 자세한 표·계산기" 쪽으로 건다. 억지 궁금증은 낚시다.

하지 말 것
- 같은 URL 3회 이상 → 저품질 신호
- 단축 URL·리다이렉트 → 네이버가 특히 싫어한다. 원본 주소 그대로
- 워드프레스 본문 복붙 → **중복 콘텐츠로 양쪽 다 죽는다.**
  블로그는 "그 질문 하나"만, 워드프레스는 "전체 비교·기능"만 맡는다

### 3-2. 실측 참고 — 경쟁글 본문 구성

> 출처와 한계는 **2-5와 동일**하다. 본문 전체를 못 읽었으므로
> **제목과 검색 요약문에서 확인된 것만** 적는다. 링크 위치·이미지 배치는 미확인.

- **`구분 / 주요 내용` 2열 표가 사실상 표준.** 현행 `table` 슬롯(3행)은 방향이 맞다.
- **Q&A를 본문에 그대로 노출**하는 글이 많다 (`Q. 보상은 어떻게 받나요?`).
  현행 `sub1`+`body1` 은 서술형인데, 소재에 따라 Q&A 형태가 더 나을 수 있다.
  단 📌 소제목 규칙(3절 표)과 충돌하지 않게 **글당 한 곳만** 시험한다.
- **`✅ 한 줄 정리` 로 닫는 마무리**가 반복 관측된다.
  현행 `question`(여운형 질문)과는 다른 방식이다. 4절의 '댓글' 금지와는 충돌하지 않으므로
  `question` **앞에** 한 줄 요약을 넣는 실험은 가능하다.

> ⚠️ 위 3가지는 **아직 A/B 검증 안 된 가설**이다. 10건 전부에 적용하지 말고
> 2~3건에만 넣어 유입 차이를 본 뒤 확정한다.

### 3-3. ⭐ 배경 사진 고르는 법 — 제목의 핵심 명사가 사진에 보여야 한다

> 홈판 가이드 5절: **"카피와 배경이 같은 얘기를 해야 한다."**
> 따릉이 글에 엉뚱한 건물 사진을 깔면 그 순간 아마추어가 된다.
> 검색 키워드를 제목에 넣었으면 **그 키워드가 사진에도 있어야** 한다.

**소재를 두 종류로 가른다. 사진이 있는 곳이 다르기 때문이다.**

| | 브랜드 (따릉이·쿠팡·서울시설공단) | 제도 (종합소득세·근로장려금·부가세) |
|---|---|---|
| 실물 사진이 | 존재한다 | **존재하지 않는다** — 찍을 물건이 없다 |
| 어디서 | Wikimedia Commons | Pexels / Unsplash 상황 컷 |
| 검색어 | 한글·영문 둘 다 시도 | **영문 소문자만** (한글은 스톡에서 0건) |
| 필수 | `verify` 게이트 | 금칙어 회피 |

검색 계획은 `_engine/topics.json` 에 키워드별로 적어둔다. 실행은 한 줄이다.

```bash
python _engine/source_photo.py --topic 종합소득세     # 사전에 있는 키워드
python _engine/source_photo.py --season 5월           # 그 시즌 전부 미리
python _engine/source_photo.py --adhoc "OO 유출" --slug oo --thumb "..." --card "..."
                                                      # 사전에 없는 긴급 키워드
```

```
'Coupang'   → 실제 쿠팡 로켓배송 트럭·프레시백      ✅
'Temu app'  → 이탈리아 Temù 마을 교회·수력발전소   ❌
'따릉이'    → 실제 따릉이                          ✅
```

브랜드마다 먹히는 표기가 다르다. **"한글로 검색하라" 같은 단일 규칙은 통하지 않는다.**
그래서 `topics.json` 의 `verify` 에 기대 단어를 적고, 결과 출처에 그게 실제로
들어있는 것만 채택한다. 없으면 폐기하고 다음 검색어로 넘어간다.
쿠팡 실측에서 이 게이트가 **매 역할당 3건씩** 걸러냈다.

> 테무처럼 Wikimedia 에 실물이 아예 없고 외국 지명과 겹치는 소재는
> **처음부터 `verify` 를 주지 말고 스톡 상황 컷으로** 보낸다. 억지로 붙이면 오매칭만 는다.

**② 제도형 검색어 금칙어 — 둘 다 "외국 티"가 난다**

| 쓰면 안 되는 말 | 나오는 것 |
|---|---|
| `document` `form` `paperwork` | 미국 세금서식(Form 1040) |
| `money` `cash` `banknote` | 달러·외국 지폐 |
| `screen` `app` `smartphone` | **폰 화면에 찍힌 남의 브랜드 로고** |
| `coins` (단독) | **암호화폐 코인** — 비트코인 심볼이 박혀 나온다 |

앞의 둘은 "외국 티"가 나서 이질감을 만든다. 한국 세금 글에 1040 서식이나 달러가 깔리면 끝이다.
세 번째는 더 위험하다 — 테무 썸네일 배경에 **Alipay 로고가 박힌 폰 화면**이 잡혀 나왔다.
경쟁 브랜드가 우리 썸네일에 들어가는 셈이다.

대신 **국적도 브랜드도 안 드러나는 사물 클로즈업**을 노린다 —
계산기 · 동전 · 영수증 · 열쇠 · 저금통 · 청진기 · 장바구니 · 택배상자.

**④ 로고는 긁지 말고 정식으로 받는다 — 대부분 Public domain 이다**

구글 이미지에 뜨는 로고는 나무위키·언론사가 재가공한 것이라 그대로 못 쓴다.
그런데 **단순 워드마크는 창작성 기준 미달이라 Wikimedia 에 PD 로 올라와 있다.**
실측(2026-08-10)에서 전부 PD/CC0 였다:

```
File:Coupang logo.svg                        1280x291   Public domain
File:Temu logo.svg                           1280x309   Public domain
File:Samsung Electronics logo (hangul).svg   1280x466   Public domain
File:SK Hynix.svg                            1280x677   Public domain
File:Bitcoin logo clean.svg                  1280x272   CC0
```

`source_photo.py` 가 `verify` 있는 소재에서 자동으로 받아 `{slug}_logo.png` 로 저장한다.
렌더할 때 넘기면 좌상단에 얹힌다.

```python
cu.build_thumbnail_svg(..., logo_path="assets/photos/temu_leak_logo.png")
```

**이게 브랜드 인지도를 만드는 가장 확실한 수단이다.** 배경 사진이 다소 밋밋해도
로고 하나가 박히면 "내 얘긴지" 판정이 즉시 된다(홈판 가이드 5절의 고유명사 조건 충족).

> 로고 검색도 오매칭이 심하다. `Temu logo` 에 인도네시아 학교 로고가 섞여 나온다.
> 파일명에 브랜드명이 실제로 들어있는 것만 채택하도록 걸러둔다.
> 검색어가 다르면 `topics.json` 의 `logo_query` 로 지정한다 (따릉이 → `Seoul Bike`).

**구글 이미지의 올바른 용도**: "어떤 그림이 맞는지" 파악하는 **참고용**이다.
거기 뜬 파일을 내려받아 쓰는 게 아니라, 보고 나서 **같은 물건을 PD·CC 소스에서 구한다.**

**③ 자동 필터로는 끝까지 못 간다 — 육안검수가 마지막 관문이다**

verify 를 통과하고도 엉뚱한 게 섞인다(쿠팡 검색에 옛 지도 스캔본 1장이 뚫고 들어왔다).
소싱이 끝나면 `assets/photos/_검수_{slug}.jpg` 몽타주가 생기므로 **반드시 보고** 지운다.

**복붙 폴더에는 `0번 본문.txt` 와 `N번 사진.jpg` 만 둔다.** 검수용 파일이나 HTML을
같이 두면 발행할 때 뭘 써야 하는지 헷갈린다 (2026-08-10 피드백).
윗줄은 원본, **아랫줄은 실제 홈판 크기(120px)** 다.

> 🔴 **몽타주만으로는 부족하다. 썸네일로 쓸 컷은 원본 크기로 한 번 더 본다.**
> 근로장려금 소싱에서 `coins in hand` 로 받은 사진이 **암호화폐 코인**이었는데,
> 몽타주 크기(220px)에서는 일반 동전과 구별이 안 됐다. 렌더하고 나서야
> 비트코인 심볼이 보였다. 정부지원금 글에 크립토가 깔릴 뻔했다.
> **1번 썸네일에 쓸 사진만큼은 원본을 열어보는 것을 절차로 둔다.**

**지킬 것**
- 라이선스가 확인된 것만 채택한다 (`Public domain` / `CC0` / `CC BY` / `CC BY-SA` / `KOGL`
  / 스톡 3사). 자동으로 걸러지고 출처는 `assets/photos/index.json` 에 남는다.
  **뉴스 보도사진 무단 전재는 금지.**
- `.gitignore` 가 `assets/photos/*` 를 무시하므로 확정한 것만 `git add -f`.
- **계절 키워드는 시즌 한 달 전에 미리 받아둔다.** 터진 날 소싱하면 검수할 시간이 없다.
  5월(종합소득세·근로장려금) · 1·7월(부가세) · 1·2월(연말정산) · 6·12월(자동차세)
  · 7·9월(재산세) · 4월(건강보험료).
- 카테고리당 5~6장 쌓아두고 순환한다. 같은 사진이 3일 연속 나오면 눈이 지나친다.

**⭐ 썸네일 배경과 본문 카드 배경은 고르는 기준이 정반대다 (2026-08-10 확정)**

같은 따릉이 사진이라도 어디에 쓰느냐에 따라 맞고 틀리고가 갈린다.

| | 썸네일 (1번) | 본문 실사카드 (2번) |
|---|---|---|
| 보이는 크기 | **120px** — 손톱만 하다 | 화면 폭 전체 |
| 골라야 할 컷 | **피사체 하나가 화면을 채우는 클로즈업** | 전경·상황 컷도 괜찮다 |
| 금지 | 원경·전경샷 (대여소 전체, 거리 풍경) | — |
| 이유 | 작은 요소 여러 개는 뭉개져서 초록 얼룩이 된다 | 크게 보므로 디테일이 오히려 산다 |

실패 사례: 따릉이 **대여소 전경**을 썸네일에 썼더니 120px에서 자전거가 아니라
초록색 덩어리로 보였다. **자전거 한 대 클로즈업**으로 바꾸니 즉시 판정 가능해졌다.
같은 사진을 본문 카드로 내리니 거기서는 오히려 잘 맞았다.

> 인스타 v13에서 "본문 슬라이드에 깔린 34~54px 불릿 3줄이 안 읽힌다"고 확정한 것과
> 같은 원리다. **작은 화면에서는 요소를 줄이고 하나를 키운다.**

**판정법 (필수)**: 렌더 후 **120px로 축소해서 눈으로 본다.**
이 크기에서 (1) 두 줄 카피가 읽히고 (2) 피사체가 뭔지 식별되면 통과.
검수용 120px 축소본은 `output/_review/` 에 뽑는다. **복붙 폴더에는 넣지 않는다** —
발행할 때 헷갈린다. (`output/_*` 는 .gitignore 가 막고 있다)
둘 중 하나라도 안 되면 사진을 바꾸거나 `dim` 을 올린다.

**dim 기준**: 사진이 밝고 복잡하면 `0.5~0.6`, 원래 어두우면 `0.3~0.4`.
글자가 안 읽히면 폰트를 줄이지 말고 **dim 을 올린다** (가독성 > 사진 선명도).

## 4-A. ⭐ 하루 발행 구조 (2026-08-10 확정 · 임의 변경 금지)

워드프레스 **2세트**, 네이버 **10건**. 세트 성격이 다르므로 글도 다르게 쓴다.

```
A세트 — 이슈                        B세트 — 롱테일
├ 메인허브                          ├ 메인허브
├ 1차 스포크                        ├ 1차 스포크
└ 2차 스포크                        └ 2차 스포크
      ↑                                   ↑
  네이버 5건                          네이버 5건
  홈판 2 + 검색 3                     롱테일 5
```

| | **A세트 (이슈)** | **B세트 (롱테일)** |
|---|---|---|
| 소재 | 따릉이 유출 · 쿠팡 유출 · 민생지원금 · 모두의카드 | 종합소득세 · 연말정산 · 부가세 · 근로장려금 · 재산세 · 자동차세 · 건강보험료 |
| 수명 | **1~2주 뒤 사망** | **매년 부활** |
| 노리는 것 | 홈판 노출 · 즉시 트래픽 | 검색 색인 · 누적 자산 |
| 착수 시점 | **터진 날 안에** | **시즌 한 달 전** |
| 글 성격 | 관점 · 차별화 | 정확 · 완결 |
| 네이버 5건 | 홈판 2 (1,000~1,300자·이미지3) + 검색 3 (400~900자·썸네일1) | 검색 5 (400~900자·썸네일1) |

**왜 이렇게 갈랐나**

이슈만 하면 자산이 안 쌓인다. 이슈 페이지는 2주 트래픽을 받고 죽으므로,
다음 이슈 때 매번 처음부터 시작하게 된다. 계절 키워드는 내년에도 살아 있어
도메인에 남는 자산이 된다. **A가 오늘의 트래픽을, B가 내년의 트래픽을 만든다.**

**A세트는 속도가 전부다.** 따릉이 실측(2026-08-10)에서 확인했다 —
경쟁 글 발행일이 통지 시작일인 7/21에 몰렸고 7/24면 이미 상위가 점유됐다.
**늦게 들어가면 "지급일 안내" 류로는 절대 못 이긴다.** 그때는 관점으로만 뚫린다.

> 백링크가 두 허브로 갈리는 건 감수한다(§0은 한 곳 집중을 권한다).
> B가 계속 살아 있는 자산이라 시간이 갈수록 회수된다고 보고 내린 결정이다.

**하루 렌더 장수**: 홈판 2×3 + 검색 8×1 = **14장**

## 5. 매일 돌리는 순서

0. **그날 선언서부터 만든다.** `_engine/day_template.json` 을 복사해
   `day_MMDD.json` 으로 만들고 A세트(이슈)·B세트(롱테일) 소재와 허브 URL을 채운다.

   - B는 **다가오는 시즌**에서. 한 달 전에 시작한다 (5월 종합소득세 → 4월에 착수).
   - `issue_started` 와 오늘이 **3일 이상 벌어지면** 정보성으로는 못 이긴다.
     제목·본문을 관점 쪽으로 완전히 틀거나, A소재 자체를 바꾼다.

   ```
   python _engine/make_spokes.py ../_set_20260809.py 0809 B
   ```
   그날 허브의 FAQ 14개(hub 4 · t1 5 · t2 5)를 스포크 10건의 뼈대로 옮긴다.
   FAQ는 이미 "사람들이 실제로 검색하는 질문" 형태이고 답변도 사실 검증을 거쳤다.
   **마지막 인자는 소재 유형(A/B)** — 소재 앞에 시·군·구를 붙여 말이 되면 A, 안 되면 B.
3. `spokes_MMDD_draft.json` 을 열어 각 post 의 `_todo` 를 처리한다.
   - 제목 → 지식iN·연관검색어를 보고 확정 (`_title_candidates` 는 후보일 뿐)
   - 표 '핵심·확인' 2줄 → 숫자·기한 위주로 짧게 고쳐 쓴다
   - 여운형 질문 → 소재에 맞게
   - `⚠ 원본 FAQ 답변이 짧아…` 표시가 붙은 글은 본문을 2~3문장 보강한다
   다 고쳤으면 `_todo` 를 지우고 `spokes_MMDD.json` 으로 rename.
   > `hub` 3개 URL은 **반드시 브라우저로 열어 200인지 확인**하고 넘어간다.
4. 저장소 루트에서 빌드:
   ```
   python _engine/build_spokes.py _engine/spokes_MMDD.json
   ```
5. `build_report.json` 의 `problems` 와 `cross_problems` 가 **둘 다 빈 배열**인지 본다.
6. `output/{MMDD}/네이버_스탠바이.html` 을 열어 복사 버튼으로 네이버에 붙여넣는다.

## 10. 발행 후 og:image 확인 (2026-08-10 사고 기록)

네이버에 URL 을 붙여넣었더니 카드 이미지가 **워드프레스 사이트 로고**로 떴다.
원인이 두 겹이었고 둘 다 조용히 실패해서 찾는 데 오래 걸렸다.

**① `rank_math_facebook_image` 가 비어 있었다**
`publish_full_post` 가 `og_image_url` 로 넘기는 `media_url` 이 빈 문자열이라
`if og_image_url.strip():` 에서 건너뛴다. 대표이미지는 정상인데 og 만 폴백된다.
덮어쓰기 경로에는 명시적 패치가 있었고 **신규 경로에만 없었다.**
→ `set_publisher` 신규 경로에 보정 추가. featured_media 를 되짚어 URL 을 확보한다.

**② Breeze + Cloudways Varnish 캐시가 옛 HTML 을 붙잡고 있었다**
```
Cache-Provider  CLOUDWAYS-CACHE-DE
Cache-Control   s-maxage=2592000     ← 30일
X-Cache         HIT
```
메타만 고치면 `save_post` 훅이 안 돌아 캐시가 안 비워진다.
쿼리스트링(`?v=2`)을 붙이면 캐시를 비켜가서 정상으로 보이는데,
**깨끗한 URL 은 계속 옛 HTML 을 뱉는다.** 이것 때문에 처음에 네이버 캐시로 오진했다.
→ 메타 패치 뒤에 글을 한 번 다시 저장해 퍼지를 발화시킨다.

### 새 소재를 처음 발행하면 반드시 확인한다

```bash
python - <<'PY'
import re, requests
u = "https://savemoney119.com/<슬러그>/"
h = requests.get(u, headers={"User-Agent":"Mozilla/5.0"}, timeout=40)
print("X-Cache", h.headers.get("X-Cache"), "Age", h.headers.get("Age"))
print(re.search(r'og:image"[^>]*content="([^"]*)"', h.text).group(1))
PY
```

`X-Cache: MISS` 이고 og:image 가 **로고가 아닌 파일명**이면 정상이다.
`HIT` 이면서 로고가 나오면 글을 다시 저장해 퍼지시킨다.

> 같은 슬러그를 덮어쓰는 B세트는 이 문제가 잘 안 드러난다.
> **새 슬러그로 처음 발행할 때만** 터진다.

### 10-1. 네이버가 옛 카드를 붙잡고 있을 때

서버를 고쳐도 **네이버가 이미 긁어둔 카드**는 안 바뀐다.
페이스북과 달리 네이버에는 캐시 초기화 도구가 없고, 언제 풀리는지 보장도 없다.

**해법: 주소 뒤에 `?v=2` 를 붙여 발행한다.**

```
https://savemoney119.com/<슬러그>/?v=2
```

- 네이버가 **새 주소로 인식해 다시 긁는다** (2026-08-10 실측으로 확인)
- `canonical` 이 원본을 가리키므로 **백링크 신호는 원본으로 모인다**
  (`?v=2` 페이지의 canonical·og:url 둘 다 깨끗한 주소였다)
- 리다이렉트가 아니라 4절 "단축 URL·리다이렉트 금지" 에 걸리지 않는다

**언제 쓰나**
- ✅ 이미 네이버에 잘못된 카드로 긁힌 주소
- ❌ 새 슬러그 — 그냥 깨끗한 주소로 쓴다.
  발행 시 캐시 퍼지가 `set_publisher` 에 들어갔으므로 처음부터 제대로 나간다.

> og 를 또 바꾸면 `?v=3` 으로 올린다. 같은 번호를 재사용하면 다시 캐시에 걸린다.
