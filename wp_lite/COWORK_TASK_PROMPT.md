**B세트의 핵심은 슬러그를 절대 안 바꾸는 것이다.**
`/jonghap-sodeukse/` 를 한 번 만들면 **내년에도 그 슬러그를 덮어쓴다.**
매년 새 글을 만들면 자산이 안 쌓이고 서로 카니발라이즈한다.
`publish_set` 이 같은 슬러그면 자동으로 update 경로를 탄다.

A세트와 달리 **마감 임박이 없어도 된다.** 대신 완결성이 생명이다 —
FAQ를 더 넣고, 계산 예시를 넣고, 매년 바뀌는 숫자(공제 한도·세율)를 갱신한다.

### 실행 방법

```python
import sys; sys.path.insert(0, "<세션 mount>/wp_lite")
from set_publisher import publish_set, verify_set
from _set_YYYYMMDD_a import SET as SET_A     # 이슈
from _set_YYYYMMDD_b import SET as SET_B     # 롱테일

urls_a = publish_set(SET_A)                  # 홈 고정은 A만
urls_b = publish_set(SET_B, sticky=False)    # ← B는 고정하지 않는다
```

**🔴 sticky 충돌 주의.** `clear_previous_sticky()` 는 `keep_id` 하나만 남기고
나머지 고정을 전부 해제한다. 그대로 두 번 호출하면 **B가 A의 홈 고정을 풀어버린다.**
홈 상단은 지금 화제인 A가 차지해야 맞다. B는 검색으로 들어오므로 고정이 필요 없다.
`publish_set` 에 `sticky` 인자가 없으면 B 발행 뒤 A를 다시 고정하거나, 인자를 추가한다.

### 네이버 블로그 10건 배분 (구해돈 저장소가 담당)

```
A세트 ← 5건   홈판 2건 (1,000~1,300자 · 이미지 3장) + 검색 3건 (400~900자 · 썸네일 1장)
B세트 ← 5건   롱테일 5건 (400~900자 · 썸네일 1장)
```

- **A 글은 A 허브로만, B 글은 B 허브로만** 링크한다. 섞으면 신호가 흩어진다.
- 글 1개당 링크 2회. **중간(25~35%)은 URL 단독+엔터로 이미지 카드**,
  **최하단은 👉 텍스트 링크.** 맨 위에는 절대 넣지 않는다(체류시간 붕괴).
- 상세 규격은 구해돈 저장소 `_engine/HANDOFF_스포크_운영.md` 3-1절·4-A절.

### 발행 후

```python

```

## 🔴🔴 2026-08-09 v7 — v8이 개수·구성을 대체함. 소재 선정·검증 규칙은 계속 유효

- **하루 10개 → 5개 → 이제 "하루 1세트(3장)".** 개수 경쟁을 완전히 접는다.
- 345개를 쌓고도 유입이 0이었던 이유는 양이 아니라 **진입점이 흩어져서**다.
  이제 하루에 **한 소재만** 다루고, 그 소재로 **거미줄 한 덩어리**를 완성한다.

### 하루 산출물 = 세트 1개 (3장)
```
메인허브 (tier 1) ─┬─ CTA① → 1차 (조회·대상확인, tier 2) ─┬─ CTA① → 2차
                   │                                        └─ CTA② → 공식 사이트
                   └─ CTA② → 2차 (신청·행동, tier 2)      ─┬─ CTA① → 공식 사이트 A
```

- **반드시 공식 사이트로 종착**한다 (정부24·복지로·해당 기관). 외부 상업 도메인 체인 금지.

### 실행 방법 — 직접 HTML 짜지 말 것
```python
import sys; sys.path.insert(0, "<세션 mount>/wp_lite")
from set_publisher import publish_set, verify_set
from _set_YYYYMMDD import SET      # 그날 데이터 파일만 새로 쓴다
publish_set(SET)                    # 검증 → 링크 자동배선 → 3장 발행 → 홈고정 → 헤더갱신
```
- `set_publisher.py`가 다음을 전부 자동 처리한다:
  슬러그 확정 → CTA 링크 배선(`_to: "t1"|"t2"|"official:0"`) → 썸네일 → 발행/덮어쓰기
  → 메인허브 홈 고정 + **어제 것 sticky 해제** → 헤더 진입로 교체 → Rank Math·og:image
- 데이터 파일(`_set_YYYYMMDD.py`)만 매일 새로 쓰면 된다. 엔진은 건드리지 않는다.
- 발행 후 `verify_set()`으로 광고·CTA·브릿지·doubt 개수와 외부링크 200을 확인한다.

### 같은 소재를 며칠 물고 늘어질 것
매일 소재를 갈아치우면 v6 이전과 같은 함정에 빠진다.
**하나의 세트는 최소 3~5일 유지**하고, 새 글을 만드는 대신 **같은 슬러그를 덮어써서**
데이터를 갱신하고 키워드만 넓힌다(`publish_set`이 자동으로 update 경로를 탄다).
소재를 바꿀 때는 `slug_base`를 새로 정한다.

### 소재 자동 선정 (사람에게 묻지 않는다)
**1순위 = 이슈·사건 중 "돈이 걸린 것".** 없으면 정책지원금·정부 할인으로 폴백한다.
점수 = 마감임박(×3) + 불확실성(×3) + 대상 규모(×2) + 금액(×2) + 지역/대상 분화 가능성(×1)
- 마감임박 : 신청·접수·소송인단 모집 등 4주 내 마감일이 있는가
- 불확실성 : "나도 대상인가"가 사람마다 갈리는가 (전 국민 공통 제도는 오히려 약함)
- 최근 14일 내 세트로 다룬 소재는 제외 (`GET /wp/v2/posts?per_page=50&_fields=title,slug,date`)
- 예: 2026-08-09 선정 = **따릉이 462만명 개인정보 유출 보상**
  (이슈 ✔ / 9월 11일 마감 ✔ / 462만명 ✔ / 5천원 vs 판례 10만원 ✔)

### 각 페이지가 반드시 갖춰야 할 것 (`set_publisher.validate()`가 강제)
- `focus`가 제목·excerpt·H2 3개 전부에 **문자열 그대로** 포함
- excerpt 110~180자, FAQ 3개 이상, 썸네일 제목 2줄 이하
- `bridge` — CTA 직전 한 줄 (없으면 검증 실패)
- `doubt` — 1차·2차는 필수. "답은 줬는데 아직 이게 남았습니다"로 다음 단계를 만든다
- `official` 최소 1개 — 거미줄 종착점

### 법률·의료 등 민감 소재 취급
소송·배상 같은 소재를 다룰 때는 **특정 법률 서비스 참여를 권유하지 않는다.**
사실 안내 + 선택지 비교 + "법률 자문이 아님" 고지를 반드시 넣고,
무료 공식 창구(분쟁조정위원회 등)를 먼저 제시한다.

### 허브 주제 자동 선정 규칙 (사람에게 묻지 말고 스스로 정한다)
아래 점수가 가장 높은 소재 1개를 그날의 허브 핵심키워드로 삼는다.

1. **지역 분화 가능성 (가중치 3)** — 시·군·구 단위로 쪼개 스포크를 10개 이상 뽑을 수 있는가.
   (예: "추석 민생지원금"은 지자체마다 금액이 달라 만점. "근로장려금"은 전국 단일이라 낮음.)
2. **시의성·마감 (가중치 3)** — 마감일이나 지급일이 4주 안에 있는가.
3. **불확실성 (가중치 2)** — "나는 되나 안 되나"가 사람마다 갈리는가.
   갈릴수록 조회 CTA가 눌린다. 전 국민 공통 제도는 오히려 약하다.
4. **금액 크기 (가중치 1)** — 1인당 10만원 이상인가.
5. **중복 제외 (감점)** — 최근 14일 내 허브로 다룬 키워드는 제외한다.
   `GET {wp_url}/wp-json/wp/v2/posts?per_page=50&_fields=title,slug,date`로 확인.

동점이면 지역 분화 가능성이 높은 쪽을 고른다.

  메뉴를 primary 위치에 붙여도 화면에 `<nav>`가 렌더링되지 않는다(메뉴 항목까지 다
  넣어봤지만 출력되지 않는 것을 확인했다).
- 실제로 사이트 전역 메뉴 역할을 하는 것은 **'헤더' 위젯 영역의 `block-25`** 하나뿐이다.

따라서 허브를 만든 직후 아래를 호출해 헤더 버튼을 그날의 허브로 교체한다:
```python
from hub_builder import set_header_hub_link
set_header_hub_link(WP_URL, WP_ID, WP_PW,
                    hub_url="https://savemoney119.com/<오늘의 허브 슬러그>/",
                    hub_label="🔥 <10자 이내 행동 문구>")
```
추가로 허브 글을 `sticky=True`(홈 최상단 고정)로 만든다:
`POST /wp-json/wp/v2/posts/{id}` → `{"sticky": true}`.
이때 **전날 허브의 sticky는 반드시 해제**한다(안 그러면 홈 상단에 계속 쌓인다).

> 참고: 홈(`/`)은 nginx 캐시(`X-Cache: HIT`, Age 수십 초)를 타므로 갱신이 1~2분 늦게
> 보일 수 있다. 확인할 때는 `?nocache=1`을 붙여서 본다. 개별 글 페이지는 즉시 반영된다.

### 🔴 계층 설계 (v3 — 벤치마크 3계층 체인 해부 결과)
분석 대상: `event.affluentneighbor.com`(1차) → `good.health-research-life.com`(2차)
→ `wellbeinghow.com`(3차) → `nhis.or.kr`(공식). 같은 애드센스 계정, 광고 슬롯 1개 재사용.

**배운 것 4가지 — `hub_builder.py`에 이미 코드로 반영되어 있다.**
1. **답을 하나 주고 새 질문을 하나 심는다.** 정보를 감추지 않는다. 준 정보가 다음
   불안을 만들도록 배치한다. → cfg의 `doubt=("제목","본문")`
   - 허브: 지역 확정 여부를 알려줌 → "근데 기준일에 주민등록이 있었나?"
   - 스포크A: 전체 목록을 줌 → "근데 신청은 어떻게?"
   - 스포크B: 절차를 줌 → "근데 지역화폐 어디서 쓰지? 기한 넘기면 소멸"
2. **CTA 직전에 브릿지 문장을 넣는다.** 버튼만 덩그러니 놓지 않는다. → cfg의 `bridge`
3. **계층이 깊어질수록 CTA는 줄이고 광고는 늘린다.** → cfg의 `tier`
   | tier | 용도 | CTA | 광고 |
   |---|---|---|---|
   | 1 | 허브 | 3회(상·중·하) | 1개 |
   | 2 | 스포크 | 2회(중·하) | 2개 |
   | 3 | 개별 상세 | 1회(하) | 2개 |
   2차부터 상단 CTA를 빼는 이유: 이미 클릭해서 들어온 사람이라 이탈이 적으므로
   **다 읽게 만든 뒤** 아래에서만 넘긴다 → 체류시간과 광고 노출을 먼저 확보한다.
4. **검색 진입점은 허브 하나로 몰아준다.** 벤치마크는 2차에 SEO를 아예 안 한다
   (meta description조차 없음) — 페이지뷰 부풀리기용이기 때문. 우리는 단일 도메인이라
   전 계층에 Rank Math를 넣되, 네이버 블로그 링크는 **허브로만** 보낸다.

**따라 하지 않는 것**: 여러 도메인에 내용 없는 랜딩을 체인으로 까는 것.
구글 doorway/PBN 판정 시 통째로 색인 삭제된다. 계층은 반드시 단일 도메인 안에서 만들고,
각 계층이 실제로 다른 정보를 담아야 한다.

## 2026-07-29 v5 갱신 — SEO 노출 점검 결과 및 수정사항

사용자가 "글이 아예 노출이 안 된다"며 Rank Math SEO 점수가 자동발행 글에서
전부 N/A로 뜨는 문제를 제보해 점검한 결과, 아래 두 가지 실제 원인을 찾아
바로잡았다. 이후 실행부터는 자동 반영되므로 별도 조치 불필요하나, 배경을
기록해둔다.

1. **Rank Math focus keyword/설명 PATCH가 처음부터 전부 조용히 실패하고 있었음**:
   `wp_publisher.py`의 구버전 `patch_post_rank_math_meta()`는 서버
   `wp-content/mu-plugins/rank-math-rest-meta.php` 설치가 선행되어야 동작하는데,
   점검해보니 이 mu-plugin이 실제로는 한 번도 서버에 설치된 적이 없었다.
   REST API는 등록되지 않은 meta 키를 에러 없이 조용히 버리기 때문에
   PATCH 응답은 계속 `ok: True`로 찍혔지만 실제로는 focus keyword/설명이
   전혀 반영되지 않았고, 그래서 워드프레스 글 목록에서 "키워드: 미설정" +
   SEO 점수 N/A로 보였던 것.
   → **해결**: 사이트에 이미 설치·활성화되어 있는 Rank Math 플러그인이 자체
   제공하는 공식 REST 엔드포인트 `POST /wp-json/rankmath/v1/updateMeta`
   (body: `{"objectType":"post","objectID":<id>,"meta":{"rank_math_focus_keyword":...,
   "rank_math_description":...}}`)를 새로 발견해 동작을 확인했다. `wp_publisher.py`에
   `patch_rank_math_meta_v2()`를 추가하고 `publish_full_post()`가 이 함수를
   기본으로 쓰도록(구버전은 폴백으로만 유지) 수정 완료 — **더 이상 mu-plugin
   설치 여부를 신경 쓸 필요 없음**.
   - 단, Rank Math의 "SEO 점수(70점 등)" 자체는 에디터에서 Rank Math JS가
     본문을 실시간 분석해야 계산되는 값이라, REST API로 만든 글은 focus
     keyword를 제대로 넣어도 점수 칸이 계속 N/A로 보일 수 있다. **이건 표시상
     문제일 뿐 구글/네이버 실제 검색 순위에 직접 반영되는 값이 아니므로
     (Rank Math 자체 안내에도 없음 — 어디까지나 작성자용 체크리스트) 점수
     자체를 억지로 채우려 하지 않는다.** 대신 아래 체크리스트를 사람이 직접
     지키는 게 진짜 순위 요인이다: 제목·H2에 focus keyword 포함(아래 3-1 갱신
     내용 참고), 메타디스크립션 120~160자, 이미지 alt에 키워드, 본문 내
     외부 출처 링크 최소 1개, 내부링크(함께 보면 좋은 글) 포함 — 이 템플릿은
     이미 대부분 충족하고 있다.
2. **워드프레스 예약발행(WP-Cron)이 가끔 정시에 안 돌 수 있음을 확인**: 2026-07-29
   실행에서 10개 중 07:00 슬롯(가장 이른 슬롯) 하나만 예약 시각이 8시간 넘게
   지나도록 `status=future`에 그대로 멈춰 있었다(나머지 9개는 정상적으로
   자동 전환됨). 신생 저트래픽 사이트라 WP 기본 pseudo-cron이 방문자 트래픽에
   의존해서 발생하는 것으로 추정된다. → **8번(결과 보고) 직전에 새 단계 추가**:
   발행 직후가 아니라, 그날 이전 슬롯들의 예약 시각이 이미 지났는데도
   `status=future`로 남아있는 글이 있는지 `GET {wp_url}/wp-json/wp/v2/posts?
   status=future&_fields=id,date,status`로 재확인하고, 있으면 즉시
   `status=publish`로 PATCH해서 강제 발행한다(날짜는 건드리지 않음 — 이미
   과거 날짜인 채로 publish 처리하면 워드프레스가 원래 예약 시각을 그대로
   유지한다). 이 사이트가 성장해서 트래픽이 늘면 자연히 덜 발생하겠지만,
   그 전까지는 이 안전장치가 필요하다.
3. **인덱싱(색인) 관련 확인 결과**: `/wp-json/` 네임스페이스 조회 결과 IndexNow
   플러그인이 이미 설치·활성화되어 있고(`AutoSubmissionEnabled: true`),
   지금까지 제출 11건 전부 성공(`FailedSubmissionCount: 0`)으로 확인됐다 —
   즉 **글을 발행할 때마다 Bing/Yandex(및 IndexNow를 지원하는 검색엔진)에는
   이미 자동으로 색인 요청이 들어가고 있어 이 부분은 추가 조치가 필요 없다.**
   다만 **구글은 IndexNow를 지원하지 않아서** 구글 노출을 앞당기려면 사용자가
   구글 서치콘솔에 직접 로그인해서 URL 검사 → 색인 생성 요청을 눌러줘야 한다
   (로그인 필요 작업이라 이 자동화가 대신할 수 없음 — 기존 "사이트 기술 설정"
   섹션에 이미 명시된 내용과 동일). 또한 이 사이트는 생긴 지 얼마 안 된
   신생 도메인이라, 기술적으로 완벽히 설정되어 있어도 검색 노출까지 보통
   수 주가 걸릴 수 있다는 점도 감안해야 한다.
4. **소제목(H2) 형식 개선**: 기존 "① 나도 받을 수 있을까?"처럼 질문형만 쓰던
   방식은 40대+ 친근함에는 좋지만, 검색 로봇이 H2만 보고 주제를 파악하기
   어렵다는 지적을 받아들여 "핵심 키워드 + 질문형" 하이브리드로 바꾼다
   (아래 공격수형 템플릿 4~9번 갱신 내용 참고).
5. **CTA 링크에 title 속성 추가**: 버튼 카피는 기존처럼 10자 이내 짧은
   행동 동사를 유지하되(모바일 UX 근거로 이미 검증된 디자인이라 문구 자체는
   바꾸지 않음), `title` 속성에 풀 설명을 추가해 링크 문맥을 보강한다.
6. **focus_keyword는 반드시 제목에 이미 등장하는 "완전한 substring"으로 고른다
   (2026-07-29 v5 2차 갱신 — 실사례로 발견한 핵심 버그, 필수 준수)**: 1차 v5
   수정 후에도 사용자가 실제 Rank Math 분석 패널을 열어보니 26/100점에
   "SEO 제목/메타설명/URL/본문 시작/본문 전체/H2/이미지 대체텍스트 어디에도
   포커스 키워드를 찾을 수 없음", "키워드 밀도 0.00"라는 결과가 나왔다. 원인은
   focus_keyword를 "생계급여 4인가구"처럼 사람이 이해하기 좋은 개념어로
   뭉뚱그려 정했기 때문 — 실제 제목엔 "4인 가구"(띄어쓰기 있음)와 "생계급여"가
   서로 떨어져 나왔지 "생계급여 4인가구"라는 붙은 문자열 자체는 어디에도
   존재하지 않았다. Rank Math는 (한글이라도) 정확한 연속 문자열 일치를 기준으로
   체크하므로, 개념적으로만 맞고 문자열이 다르면 전부 실패로 뜬다.
   → **올바른 순서**: (a) 먼저 4번 항목의 "제목 공식"대로 제목을 완성한다.
   (b) 완성된 제목 문자열 안에서 그대로 잘라낸 2~5어절짜리 부분 문자열을
   focus_keyword로 고른다(새로 창작하지 않는다 — 반드시 `focus_keyword in title`이
   참이어야 함). (c) 본문 인트로 첫 문장(또는 두 번째 문장 안)에 그 문자열을
   토씨 하나 안 틀리고 그대로 한 번 이상 넣는다(굵게 강조해도 좋음). (d) 위
   6번(신설) H2 4개 전부에 그 문자열을 동일하게 그대로 삽입한다(이미 5번
   항목에서 "핵심 키워드 + 질문형"으로 정했는데, 여기서 "핵심 키워드" =
   반드시 이 focus_keyword 문자열 그대로). (e) excerpt(메타디스크립션)에도
   동일 문자열을 그대로 포함시킨다. (f) 썸네일 `alt_text`도 전체 제목 대신
   이 focus_keyword 문자열이 들어간 짧은 문구로 지정한다(`publish_full_post()`
   호출 시 `thumbnail_alt` 인자로 명시 — 비워두면 제목 전체가 들어가는데,
   제목 전체엔 focus_keyword가 있어도 되지만 없을 수도 있어 명시가 안전).
   (g) `publish_full_post()` 호출 시 `focus_keyword`와 `excerpt`는 물론, 새로
   추가된 `patch_rank_math_meta_v2()`의 `seo_title` 인자(=title 그대로)도
   자동으로 채워지도록 이미 코드 수정 완료 — SEO Title(rank_math_title) 메타를
   명시적으로 안 채우면 사이트 전역 제목 템플릿에 의존하게 되는데 그 템플릿이
   기대와 다르게 풀려서 "제목에 키워드 없음" 오판이 나는 사례가 있었다.
   - 참고: "본문 길이 최소 600단어" 경고는 Rank Math가 영어처럼 띄어쓰기
     기준으로 단어를 세기 때문에 한국어(교착어라 조사가 붙고 띄어쓰기가
     영어보다 훨씬 적음)에서는 실제 분량이 충분해도(900~1200자) 항상 낮게
     나오는 구조적 오탐에 가깝다. 이 사이트의 900~1200자 분량 기준(40대+
     가독성 우선 설계)은 그대로 유지하고, 이 경고 자체는 무시해도 된다 —
     굳이 영어 기준에 맞추려고 내용을 억지로 늘리지 않는다.

     아직 검색엔진 신뢰도(도메인 authority)가 쌓이지 않아서, 경쟁 강도가 센
     범용 키워드(예: "청년 지원금", "전기요금 할인")를 제목의 중심 키워드로
     잡으면 상위 노출은커녕 색인조차 잘 안 된다. 따라서 아래 세 가지 방법 중
     최소 하나 이상을 적용해 제목을 최대한 좁고 구체적으로("뾰족하게") 잡는다.
     1. **지역 세분화**: "청년 지원금"이 아니라 "인천 영종구 청년 이사비
        지원"처럼 시·군·구 단위까지 좁힌다. 전국 단위 제도라도 지자체별
        추가 시행 사례가 있으면 그 지역명을 제목 앞에 붙인다.
     2. **타겟 세분화**: "지원금 총정리"가 아니라 "신혼부부", "다자녀가구",
        "프리랜서·예술인"처럼 특정 생애주기·직업군·가구 형태로 좁힌다.
     3. **트렌드/정책 선점**: 방금 발표됐거나 마감이 임박한 정책·이벤트를
        빠르게 다뤄서, 경쟁자가 아직 다루지 않은 키워드 자리를 먼저 차지한다
        (예: "9월 종료", "2차 배포", "8월 1일 접수 시작"처럼 시의성 신호를
        제목에 직접 포함).
   - **제목 공식 (2026-07-26 v4 신설)**: 위 세 가지 니치 좁히기는 결국 아래 공식의
     "메인 키워드"를 뾰족하게 잡는 방법들이다 — 최종 제목은 항상
     **메인 키워드(니치 좁힌 핵심어) + 서브 키워드(1-2단계에서 수집한 연관검색어) +
     후킹 문구(숫자·마감일·대상 등 구체적 정보)** 세 요소를 모두 포함해 조립한다.
     단, "충격!", "이것만 알면" 같은 검색 의도와 무관한 유튜브식 후킹은 쓰지
     않는다 — 후킹은 어디까지나 실제 검색 의도에 부합하는 구체적 정보(금액·기한·
     대상)여야 한다.
   - **SEO/AEO/GEO 동시 고려**: 검색엔진(SEO)뿐 아니라 AI 답변엔진(AEO)과
     생성엔진(GEO)이 인용하기 좋은 형태를 항상 함께 고려한다 — 제목/H2에
     핵심 키워드를 자연스럽게 배치하고, 도입부 첫 문단에 "무엇을·얼마를·누가"
     핵심 답을 바로 제시하며, H2/H3 소제목 구조와 리스트를 명확히 써서 AI가
     발췌·인용하기 쉽게 만든다.
   - **검색 의도 + 클릭 유발 훅 동시 충족**: 제목은 (a) 실제 사람들이 검색창에
     칠 법한 현실적인 문구여야 하고, (b) 동시에 "이건 눌러봐야겠다"는 행동
     유발 요소(구체적 금액·마감일·대상 인원 등 숫자, "놓치면", "소진 임박",
     "마감" 같은 긴급성 신호)를 포함해야 한다. 정보만 나열하는 밋밋한 제목
     (예: "OO 지원금 안내")은 지양하고, 숫자/기한/대상을 구체적으로 박아
     넣은 제목(예: "OO 이사비 최대 40만원, 8월 1일 접수 시작")을 쓴다.

3. 선별한 항목 각각을 아래 "타입별 구조 템플릿"에 맞춰 완전히 새로 집필한다
   (원문 재구성 금지, 전면 재작성). 원문 기사는 절대 그대로 베끼지 않는다 —
   사실관계만 참고하고 문장은 100% 새로 쓴다.

   ### 공통 원칙 (두 타입 모두 적용)
   - **본문에 특정 날짜("YYYY년 MM월 DD일 기준")를 하드코딩하지 않는다 (2026-07-22 갱신)**:
     롱테일/에버그린 글은 내년, 후년에도 계속 검색 유입이 들어오는데, 본문에 작성
     당시 날짜가 박혀 있으면 나중에 읽는 사람이 "어, 작년 글이네" 하고 바로 이탈한다.
     최신성 신호가 꼭 필요하면 특정 날짜 대신 "최신 기준", "현재 기준"처럼 상대적
     표현을 쓰거나, 정책 변경 가능성을 안내하는 문장("금액·조건은 매년 조금씩 바뀔
     수 있으니 신청 전 최신 공고를 꼭 확인하세요")으로 대체한다. 발행일 자체는 이미
     테마가 글 상단에 자동 표시하므로("7월 22, 2026 작성자: Ww" 형태) 본문에서
     또 언급할 필요가 없다. 단, 신청기한처럼 실제로 마감이 있는 정보(예: "7월
     31일까지")는 이 규칙과 무관하게 그대로 명시한다 — 이건 "작성일"이 아니라
     "사실 정보"이기 때문이다.
   - **문단(`<p>`)은 1~2문장마다 끊는다 (2026-07-22 갱신, 기존 "3줄 넘으면 여백"
     규칙 대체)**: PC 화면에서는 3문장을 한 문단에 묶어도 괜찮아 보이지만, 모바일은
     가로 폭이 좁아서 같은 3문장이 5~6줄로 꺾여 보이고 그러면 여러 문단이 그냥
     벽돌처럼 붙어 보인다. 그래서 문단 길이를 "줄 수" 기준이 아니라 "문장 수"
     기준으로 정한다 — 한 문단에는 1문장, 많아도 2문장까지만 넣고 그다음은 새
     `<p>`로 분리한다. (CSS 쪽에서도 모바일 `<p>` 하단 여백을 22px로 넓혀뒀으니,
     본문 작성 시 이 규칙만 지키면 자동으로 시각적 여백이 확보된다.)
   - **목차(ez-toc) 항목 간 여백은 CSS로 사이트 전역에 이미 적용되어 있다
     (2026-07-22)**: H2/H3 구조를 정상적으로 쓰면 플러그인이 자동 생성하는
     목차에 항목별 여백이 자동으로 들어간다 — 글 작성 시 별도 조치 불필요.
   - SEO: 키워드를 제목/H2/첫 문단에 자연스럽게 배치.
   - GEO(생성엔진 최적화): 명확한 소제목(H2/H3) 구조, 핵심 답을 첫 문단에 바로 제시,
     리스트/표로 스캔하기 쉽게 구성 — AI 검색엔진이 인용하기 좋은 형태로.
   - **논리 연결어로 인과관계 명시 (2026-07-26 v4 신설)**: 정보를 그냥 나열하지
     않고 "따라서", "그러므로", "결과적으로", "~때문에" 같은 접속어로 조건→결론을
     연결한다 (예: "소득 기준을 넘으면 감액 대상이 된다. 따라서 신청 전에 본인
     소득분위부터 확인하는 게 순서다"). AI 답변엔진이 답변을 추출할 때 이런
     인과 구조를 우선적으로 가져다 쓴다 — 단, 문장은 여전히 "1문장 1정보,
     20단어 이내" 원칙을 지킨다.
   - 분량: 900~1200자.
   - **40대+ 가독성 원칙 (최우선)**: 이 사이트의 핵심 타겟은 스마트폰으로 글을
     읽는 40대 이상이다. 검색엔진보다 "이 사람이 실제로 이해하고, 저장하고,
     공유하고 싶은가"를 항상 우선한다.
     - 한 문장에는 정보 1개만. 문장은 짧게 끊는다 (한 문장 20단어 넘기지 않기).
     - 어려운 한자어·전문용어가 처음 나올 때는 반드시 괄호로 쉬운 말을 덧붙인다
       (예: "기준 중위소득(정부가 정한 소득 기준선)").
     - 소제목은 딱딱한 명사형보다 "질문형"을 우선한다 — "① 신청 자격"보다
       "① 나도 받을 수 있을까?"처럼 독자가 자기 얘기처럼 느끼게 쓴다.
     - **색상 강조 (파랑=긍정 / 빨강=주의·긴급)**: 지원금액·받을 수 있는 혜택처럼
       긍정적인 정보는 `<span class="sm-positive">지원금액 최대 480만원</span>`처럼
       파란색으로, 마감기한 임박·탈락 사유·주의사항처럼 부정적이거나 긴급한
       정보는 `<span class="sm-negative">7월 31일까지</span>`처럼 빨간색으로
       감싼다. 문단마다 1~2곳만 강조하고 남발하지 않는다 (색이 너무 많으면
       오히려 눈에 안 들어옴).
     - **나열형 정보는 한 줄에 하나씩**: "1인 가구 OO만원, 2인 가구 OO만원,
       3인 가구 OO만원"처럼 여러 항목(가구원수별/소득분위별/단계별 등
       "N인·N차·N단계" 형태)을 한 문장에 쭉 나열하지 않는다. 표(table)로
       정리할 수 있으면 표를 우선 쓰고, 본문 서술 중 나열이 필요할 때는
       아래처럼 항목별로 줄을 바꾼다:
       ```
       1인 가구: OO만원<br>
       2인 가구: OO만원<br>
       3인 가구: OO만원
       ```
       이 규칙은 가구원수뿐 아니라 유사한 모든 나열형 정보(예: 소득 1분위·2분위,
       1단계·2단계·3단계 등)에 동일하게 적용한다.

   ### A. 공격수형 (정부지원금·할인정보) 구조 템플릿
   토스피드(공감형 도입/친근한 문체)·뱅크샐러드 매거진(누가→얼마나→어떻게→CTA
   4단 논리구조)·실제 상위노출 중인 개인 워드프레스 블로그(혜택노트/지원모아/
   복지24 등 — 표·숫자예시·FAQ·단일 CTA)의 장점만 뽑아 40대+ 눈높이로 재구성한
   뼈대. 목표는 정보 전달을 넘어 "저장하기·공유하기"가 일어나는 글.

   1. **제목**: "OO 신청 자격·금액·방법" 형태로 연도 + 핵심 키워드 3종(자격/금액/방법
      또는 대상/지원금액/신청방법) 포함.
   2. **도입부 (2~3문장, 토스피드 스타일 공감형)**: 딱딱한 정의문으로 시작하지
      않는다. "OO 놓치고 계신 건 아니죠?" 처럼 공감형 질문이나 짧은 상황
      제시로 열고, 곧바로 핵심 답(무엇을·얼마나·누가)을 쉬운 말로 제시한다
      (AEO 대응 겸 40대+ 이해도 확보).
   3. **저장용 요약카드** (bullet 3개, 강조 박스): 대상 / 지원금액 / 신청기한을
      한눈에. "아래 3줄만 저장해두면 끝!" 같은 문구를 카드 위에 붙여 캡처·저장
      행동을 직접 유도한다.
   3-1. **H2 소제목 형식 (2026-07-29 v5 갱신 — 필수 적용)**: 아래 4~9번 H2들은
      전부 "[핵심 키워드] + 질문형" 하이브리드로 쓴다 — 질문형만 쓰면 40대+
      독자에게는 친근하지만 검색 로봇이 H2만 보고 이 글이 무슨 글인지
      파악하기 어렵다. 예: "나도 받을 수 있을까?" (X) → "노란우산공제
      가입 자격, 나도 받을 수 있을까?" (O). 핵심 키워드는 앞서 정한
      focus_keyword 또는 제목의 메인 키워드를 그대로 재사용한다.
   4. **H2 ① [핵심 키워드] 신청 자격, 나도 받을 수 있을까?**: 조건을 표(table)로 정리하되
      열은 최대한 단순하게(2~3열). 어려운 기준 용어는 괄호로 풀이. 소득 기준 등은
      "정확한 금액·기준은 관할 기관에 확인 필요"라고 덧붙인다.
   5. **H2 ② [핵심 키워드] 지원금액, 얼마나 받을 수 있을까?**: 표 + 반드시 구체적 숫자 예시
      1개 포함 (예: "2인 가구라면 월 OO만원, 최대 OO개월이니 총 OO만원이에요"
      — 딱딱한 수식이 아니라 말하듯 풀어서).
   6. **H2 ③ [핵심 키워드] 신청 방법, 어떻게 하면 될까?**: 번호 리스트로
      단계화, 한 단계당 한 문장. 정부 공식 출처(복지로, 정부24, 관할 부처 등)
      링크를 텍스트 링크로 반드시 포함 (E-E-A-T 신뢰 신호 — 스타일드 버튼이
      아니어도 됨).
   7. **CTA 버튼**: 이 글 전체에서 딱 1번만, ③ 섹션 바로 다음에 배치한다. 본문
      최상단이나 글 끝에 중복 배치하지 않는다 (경쟁사 3곳 모두 CTA를 1회만 씀).

      **`title` 속성 추가 (2026-07-29 v5 신설)**: 버튼 표시 문구는 아래 규칙대로
      짧게 유지하되, `<a class="wide-btn" href="..." title="...">` 형태로
      `title` 속성에 "[핵심 키워드] + 목적지 설명"을 풀어서 넣는다 (예:
      `title="KB Pay 바로할인 체크카드 등록 페이지로 이동"`). 화면에 보이는
      버튼 문구는 그대로 짧게 두면서, 검색 로봇과 스크린리더에는 더 명확한
      문맥을 준다.

      **카피 규칙 — 짧을수록 좋다, 단 행동 유발 동사는 반드시 포함:**
      - 화살표(») 제외 공백 포함 10자 이내를 기본으로 한다 (bokji24의
        "지원금 신청 »" 6자가 좋은 기준).
      - "더보기" / "자세히 보기" 처럼 행동이 모호한 카피는 금지 — 반드시
        "~하기" / "~받기"로 끝나는 구체적 행동 동사를 넣는다.
      - 아래 4가지 기본형 중 소재 성격에 맞는 것을 고른다:
        1. 기본형(자격이 비교적 명확할 때): "{핵심키워드} 신청하기 »"
           예: "지원금 신청하기 »", "월세지원 신청하기 »"
        2. 확인형(자격 조건이 사람마다 갈릴 때): "자격 확인하기 »"
        3. 긴급형(신청기한이 임박했을 때만): "지금 신청하기 »"
        4. 할인/혜택형(정부지원금이 아닌 할인·쿠폰류): "할인 받기 »"
   8. **H2 ④ [핵심 키워드] 주의사항, 이것만은 꼭 확인하세요**: 탈락 사유·흔한 실수 등 실전 팁.
   9. **H2 ⑤ [핵심 키워드] 관련 FAQ, 이런 것도 궁금하시죠? (2026-07-26 v4: 2~3개 → 5개로 증량)**:
      5개, 실제 사람들이 헷갈려하는 구어체 질문으로 ("~인데 저도 받을 수
      있나요?" 식). 딱딱한 문어체 질문 지양. 질문은 1-2단계에서 수집한
      연관검색어·구어체 질문을 최우선으로 재사용한다. 답변은 각 2~4문장,
      첫 문장에 바로 결론부터 쓴다. FAQ 개수를 5개보다 더 무리하게 늘리지
      않는다 — 의미 없는 질문을 억지로 채우면 오히려 스팸 신호가 된다.
   10. **마무리 한 줄 팁 + 공유 유도**: 소금쟁이 톤으로 짧은 실천 팁 한 줄을 쓴 뒤,
       "이 글이 도움이 되었다면 가족이나 지인에게 카카오톡으로 공유해주세요"
       처럼 명시적인 공유 유도 문장을 반드시 덧붙인다 (기존 카카오톡 공유 버튼
       `gp-share-*` 컴포넌트와 자연스럽게 연결).
   11. **함께 보면 좋은 글 (2026-07-26 v4: 텍스트 링크 → 썸네일+제목 카드형으로
       변경)**: 관련 기존 게시물 2~3개를 내부링크한다. 사이트에 관련글 카드
       플러그인이 설치돼 있지 않으므로(2026-07-26 확인 완료 — CRP/YARPP/Jetpack
       관련글 미설치), 인라인 스타일로 직접 카드를 만든다. 발행 스크립트에서
       각 관련 글의 제목·링크·썸네일을 `GET {wp_url}/wp-json/wp/v2/posts?search=
       {키워드}&per_page=3&_embed=1` 로 조회해 `_embedded['wp:featuredmedia'][0]
       ['source_url']`(featured_media가 없으면 스킵하고 텍스트 링크로 대체)을
       가져온 뒤 아래 형태로 삽입한다:
       ```html
       <h3>함께 보면 좋은 글</h3>
       <div style="display:flex;gap:12px;flex-wrap:wrap;margin:16px 0;">
         <a href="{link}" style="display:block;width:160px;text-decoration:none;color:inherit;">
           <img src="{thumb_url}" alt="{title}" style="width:100%;height:84px;object-fit:cover;border-radius:8px;">
           <p style="font-size:14px;margin-top:6px;line-height:1.35;">{title}</p>
         </a>
         <!-- 2~3개 반복 -->
       </div>
       ```
       관련글 검색 결과가 비어 있으면(신생 사이트라 아직 관련 글이 부족한 경우)
       기존처럼 텍스트 링크(`<ul><li><a>`)로 조용히 폴백한다 — 에러를 내지 않는다.

   ### B. 수비수형 (경제 위인 명언·스토리) 구조 템플릿
   목적은 클릭/전환이 아니라 체류시간과 사이트 전체 신뢰도. CTA는 넣지 않거나
   아주 약하게(예: "다른 절약 팁도 보기" 텍스트 링크 정도)만 넣는다. 광고도
   최소화해 상업적 느낌을 줄인다.

   1. **제목**: "OO(인물)에게 배우는 절약/투자 습관 - 핵심 3가지" 형태.
   2. **도입부**: 인물 소개 2~3문장 (언제, 어떤 업적으로 유명한지).
   3. **H2 관련 일화·명언**: 검증 가능한 실제 일화 또는 명언 1~2개, 출처 맥락 설명.
   4. **H2 오늘날 적용할 수 있는 교훈**: 그 일화에서 끌어낼 수 있는 절약/재테크
      교훈 2~3개, bullet로.
   5. **H2 지금 바로 실천하는 방법**: 위 교훈을 savemoney119 성격에 맞게 오늘의
      실천 팁으로 자연스럽게 연결 (정부지원금 급의 CTA는 넣지 않음).
   6. **마무리 + 공유 유도**: "이런 이야기, 부모님이나 친구에게도 들려주고
      싶으시다면 카카오톡으로 공유해주세요" 처럼 부담 없는 공유 유도 한 줄을
      덧붙인다 (공격수형과 톤은 다르되 공유 유도 자체는 동일하게 넣는다).
   7. **함께 보면 좋은 글**: 관련 절약/지원금 글 2~3개 내부링크로 자연스럽게 유도.
      공격수형과 동일하게 11단계의 썸네일+제목 카드형으로 넣는다 (관련 글이
      없으면 텍스트 링크로 폴백하는 규칙도 동일).

   ### 광고 배치 규칙 (공통)
   경쟁 4개 사이트(혜택노트/지원모아/복지24/SBFC) 모두 본문 중간에 강제 배너
   광고를 넣지 않았다 — 이미 적용 중인 구글 Auto Ads(앵커+전면)로 충분하다는
   근거로 삼는다. `.ad-slot`을 본문에 수동으로 추가할 경우:
   - CTA 버튼 바로 앞/뒤에 붙이지 않는다 (오클릭 유발, 애드센스 정책 리스크).
   - 넣는다면 FAQ 섹션 이후, "함께 보면 좋은 글" 이전 1곳으로 제한한다.

4. 각 글에 대해 제목, 슬러그(영문), 카테고리, 태그 3~4개, excerpt(메타디스크립션),
   focus keyword를 정한다.

### ⭐ 2026-08-09 v4 갱신 — 썸네일은 이제 `make_og_thumbnail()`을 쓴다

**왜 바뀌었나 (실측)**: 네이버 블로그에 허브 URL을 넣으면 링크 카드가 뜬다.
그 카드는 이미지 아래에 og:title 과 og:description 을 **이미 보여준다.**
그런데 기존 썸네일은 제목을 그대로 이미지에 박아서, 카드에서 같은 말이 두 번 나왔다.
정보가 중복되니 클릭할 이유가 안 생긴다.

또 하나 — **네이버 카드는 og:image 의 좌우를 잘라낸다.** 실제로 우하단
`savemoney119` 브랜드명이 `savemoney11` 로 잘린 것을 확인했다.

그래서 규칙이 이렇게 바뀌었다.

- 이미지는 **제목을 반복하지 않는다.** "눌러야 하는 이유" 하나만 담당한다.
- 핵심 요소는 **가운데 정사각형(630x630) 안**에 넣는다. 브랜드는 그 바깥(잘려도 무방).
- 아래쪽에 **흰 알약 버튼 + ▶** 를 넣어 손가락이 가게 만든다.

**세트 cfg 에 아래 3개 필드를 반드시 넣는다** (없으면 기존 필드로 폴백되지만
제목이 반복돼서 효과가 크게 떨어진다):

```python
"thumb_eyebrow": "462만명 유출",        # 윗줄 작게 — 규모·근거
"thumb_hook": ["나도", "대상일까?"],     # 큰 글씨 2줄, 2줄째가 포인트 레드
"thumb_cta": "가입 시기로 1분 확인",     # 흰 버튼 문구 (▶ 는 자동으로 붙는다)
```

**⭐ 계층마다 후크를 다르게 쓴다 (v4.1 — 하나로 고정하지 말 것)**

| 페이지 | 후크 전략 | 예 |
|---|---|---|
| 메인허브 | **자기대입 질문** — 아직 아무것도 모르는 사람 | "나도 / 대상일까?" |
| 1차 | **손실 + 마감** — 대상인 걸 확인한 사람을 움직인다 | "안 쓰면 / 3개월 뒤 소멸" |
| 2차 | **몰랐던 정보** — 1차 정보를 이미 아는 사람 | "5천원이 / 끝이 아니다" |

순서가 중요하다. "안 쓰면 3개월 뒤 소멸"이 가장 강한 문구지만, 쿠폰이 있는지도
모르는 사람에게 첫 화면으로 던지면 무슨 말인지 모른다. 허브는 진입이라 질문형이 맞다.

작성 규칙
- `thumb_hook` 은 위 표의 계층별 전략을 따른다.
  제목을 그대로 복사하지 않는다. 한 줄 **4~7자**, 길면 폰트가 줄어 약해진다.
- `thumb_eyebrow` 는 숫자나 마감이 든 짧은 근거 한 줄. **12자 이내.**
- `thumb_cta` 는 **행동 동사 + 소요시간**. "1분 확인", "3분이면 끝" 같은 것.
  화살표(`➜` `→`)를 직접 쓰지 말 것 — 한글 폰트에 글리프가 없어 두부(□)로 깨진다.
  함수가 `▶` 로 알아서 붙인다.
- 근거 없는 문구를 넣지 않는다. 숫자·기한은 반드시 본문에 있는 사실이어야 한다.

```python
from thumbnail_gen import make_og_thumbnail
thumb = make_og_thumbnail(f"/tmp/thumb_{slug}.jpg",
                          eyebrow=c["thumb_eyebrow"],
                          hook_lines=c["thumb_hook"],
                          cta_text=c["thumb_cta"])
```

### ⭐⭐ 카드용 제목·설명도 따로 쓴다 (`og_title` / `og_desc`) — 이게 썸네일보다 중요하다

네이버 링크 카드는 **네 조각**이다. 이미지만 잘 만들어봐야 나머지가 검색엔진용 문장이면
소용이 없다. 사람은 이미지에서 멈추고, **제목과 설명을 읽고 클릭을 정한다.**

```
[이미지]
og:title          ← 카드에 이 줄이 뜬다
og:description    ← 앞부분만 뜨고 뒤는 '…' 로 잘린다
savemoney119.com
```

실측(2026-08-09): 기존 og:description 이 117자였는데 네이버 카드에서 **뒤가 잘렸다.**
앞 40자가 "대상이 462만명입니다" 라 이미지가 한 말을 반복하고 있었다.

그래서 세트 cfg 에 아래 2개를 **추가로** 넣는다. SEO용 `title` / `excerpt` 는 그대로 둔다.
`set_publisher` 가 Rank Math 의 facebook/twitter 메타에만 따로 박아 넣는다
(실제로 반영되는 것을 라이브에서 확인함).

```python
"og_title": "따릉이 유출 462만명 나도 대상일까",     # 20자 내외, 쉼표 금지
"og_desc":  "가입한 적 있으면 대상일 수 있습니다. 문자를 못 받았어도 그렇습니다. "
            "공단이 제때 통보하지 않은 것이 이번 사고의 핵심 지적사항이었기 때문입니다. "
            "가입 시기만 고르면 1분 안에 확인됩니다.",   # 100자 내외
```

작성 규칙
- `og_title` 은 **20자 내외**. 쉼표를 쓰지 않는다 (잘리면 뒤 절반이 통째로 날아간다).
  SEO 제목을 그대로 복사하지 않는다. 키워드 나열이 아니라 한 문장으로 읽혀야 한다.
- `og_desc` 는 **앞 40자가 전부라고 생각하고 쓴다.** 뒤는 잘린다.
  - 앞 40자에는 **이미지가 하지 않은 말**을 넣는다. 이미지가 "나도 대상일까?" 라고
    물었으면, 설명은 "가입한 적 있으면 대상일 수 있습니다" 라고 답을 반쯤 준다.
  - 숫자·조건·반전("문자를 못 받았어도")을 앞으로 당긴다.
  - 총 100자 내외. 그 뒤는 검색엔진용 보너스라고 본다.
- 근거 없는 문구 금지. 본문에 있는 사실만 쓴다.

`set_publisher.publish_set()` 은 **이미 이 함수로 전환됐다.** 세트 발행 경로를
쓰면 위 3개 필드만 채우면 되고 별도 호출은 필요 없다.

아래 make_thumbnail 설명은 **세트 밖의 개별 글**(구버전 경로)에만 해당한다.

7. **발행 시각 분산 (하루 10개를 자연스럽게 흩어서 예약발행, 2026-07-23 v3)**:
   - **(2026-08-08 v6로 대체)** 발행 시각은 5개 기준·120~180분 간격으로 계산한다:
     ```python
     import random
     from datetime import datetime, timedelta
     t = datetime.strptime("2026-01-01 07:00:00", "%Y-%m-%d %H:%M:%S")
     times = [t.strftime("%H:%M:%S")]
     for _ in range(4):                       # 10개 → 5개
         t += timedelta(minutes=random.uniform(120, 180))   # 60~90 → 120~180
         times.append(t.strftime("%H:%M:%S"))
     # 결과: 07:00 ~ 19:00 사이에 5개가 넓게 분산된다. 1번 슬롯(07:00)은 항상 허브.
     ```
   - 계산된 10개 시각 전부를 `status="future"` + `date`(사이트 로컬시간,
     "YYYY-MM-DDTHH:MM:SS")로 지정해 워드프레스 네이티브 예약발행을 건다.
     cron이 새벽 6:30에 돌기 때문에 07:00 슬롯도 아직 미래이므로 기본적으로
     10개 전부 future로 건다.
   - 만약 실행 시각이 늦어져(장애 등으로 재실행 등) 이미 지나버린 슬롯이
     있다면, 그 슬롯의 글만 `status="publish"`로 즉시 발행하고 나머지는
     future로 건다.
   - 매번 정확히 같은 간격(예: 항상 정확히 90분)으로 고정하지 않는다 —
     정형화된 패턴은 스팸 필터에 오히려 더 잘 걸린다.
   - 수비수형(경제 위인) 소재는 오전 7시 대표 슬롯에 배치하지 않고 오후~저녁
     슬롯 중 하나로 돌려서, 오전에는 항상 트래픽 견인용 공격수형 글이 먼저
     노출되게 한다.

7-1. **예약발행 정상 전환 확인 (2026-07-29 v5 신설)**: 모든 글을 `future`로 예약한
   뒤, 바로 다음 실행(다음날 새벽) 시작 시점에 `GET {wp_url}/wp-json/wp/v2/posts?
   status=future&_fields=id,date,title` 로 조회해서 예약 시각이 이미 지났는데도
   `future`로 남아있는 글이 있는지 확인한다. 있다면(=WP-Cron이 정시에 못 돈 경우)
   해당 글만 `status=publish`로 PATCH해서 강제 발행한다(날짜는 그대로 둔다 —
   이미 과거 날짜라 publish 처리해도 원래 예약 시각이 유지된다). 최종 리포트에
   이런 강제 발행이 있었다면 몇 건인지 함께 남긴다.

8. 발행 완료 후, 오늘 다룬 10개 글의 제목·URL·발행상태(즉시/예약 시각)·썸네일
   업로드 성공 여부를 요약해서 알려달라 (예약 작업 결과 리포트로 남는다 —
   실제 사람 확인은 사후에 훑어보는 정도로만).

## 하지 않을 것
- 쿠팡 상품 크롤링, 붕어빵틀, 네이버 블로그, IP 테더링 등 이전 프로젝트의 무거운 기능은
  이 작업에 포함하지 않는다.
- 원문 기사를 15단어 이상 그대로 인용하지 않는다.
- **트래픽 슬롯(봇 클릭) 구매, 만료 도메인(특히 정부기관 이력) 매입은 하지 않는다**
  (2026-07-26 v4 신설) — 순위 조작·사이트 평판 남용으로 간주될 수 있어 네이버/구글
  정책 위반 리스크가 실익보다 크다.
- **커뮤니티(카페/오픈채팅 등) 소량 유입 전략은 이 워드프레스 자동발행 파이프라인
  범위 밖**(2026-07-26 v4 신설)이다. 하고 싶다면 별도 작업으로 분리해서 요청할 것
  — 이 문서는 워드프레스 자연 노출(SEO/AEO/GEO)에만 집중한다.

## 사이트 기술 설정 (2026-07-26 1회 점검, 매일 자동 체크 대상 아님)
- `robots.txt` 확인 결과 `Allow: /`만 있고 GPTBot·PerplexityBot·ClaudeBot·
  Google-Extended·Bingbot을 막는 규칙이 없음 — AI 크롤러 차단 문제 없음 (양호).
- `sitemap_index.xml`이 robots.txt에 등록돼 있고 발행 시 자동 갱신되는 워드프레스
  기본 사이트맵을 그대로 사용 중 — 별도 조치 불필요.
- 네이버 서치어드바이저·구글 서치콘솔·빙 웹마스터도구 3곳에 사이트/사이트맵이
  실제로 "등록"돼 있는지는 각 콘솔 로그인이 필요해 이 자동화가 대신 확인할 수
  없다 — 사용자가 각 콘솔에서 직접 1회 확인/등록해야 한다 (미등록 시 색인 속도만
  느려질 뿐 발행 자체는 정상 진행되므로 이 작업의 실행을 막지는 않는다).
